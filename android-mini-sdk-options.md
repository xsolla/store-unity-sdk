# Варианты интеграции Android SDK в Unity / Unreal

## Сравнительная таблица

|---|----------|-------------|--------------------|-----------------------|---------------------|----------------------|
| 0 | Ничего не делать | ~100+ JAR | нет | — | нет | нет |
| 1 | Мини-SDK (те же контракты) | ~5-10 | нет | да | нет | средняя |
| 2 | Мини-SDK (новый контракт, HTTP → Unity) | 0-1 | значительные | да | да (в каждом движке) | высокая |

## Плюсы и минусы

| # | Плюсы | Минусы |
|---|-------|--------|
| 0 | Нет работы | ~100+ JAR в проекте; конфликты зависимостей; Kotlin в Unity; сложно поддерживать |
| 1 | Нет изменений в Unity; переиспользуется в Unreal/других движках; один раз сделал — всё работает | Нужно написать Android SDK с нуля на Java; при изменениях в основном SDK — ручная синхронизация |
| 2 | 0-1 зависимость; чистая архитектура; Android = тонкий UI клиент | Бизнес-логика дублируется в каждом движке; значительные изменения в Unity C#; риск расхождения реализаций |
| 3 | 0 зависимостей; полный контроль; нет отдельной библиотеки | Нет переиспользования — то же самое для Unreal и других движков; Java код живёт в Unity репозитории |
| 4 | Нет дублирования; изменения в одном месте | Требует согласования с Android командой; всё ещё Kotlin; зависимостей меньше, но не ноль |

## Подробное описание вариантов

### Вариант 0 — Ничего не делать

Продолжать использовать текущий Android SDK как есть.

**Текущее состояние:**
- 6 Maven зависимостей → ~100+ JAR/AAR после резолва транзитивных зависимостей
- Kotlin runtime и stdlib тянутся в Unity проект
- Периодические конфликты версий библиотек (okhttp, gson и др.) с другими плагинами
- Unity использует лишь ~10 из 56 методов XLogin и малую часть XPayments

**Когда имеет смысл:** если конфликтов зависимостей нет и в ближайшее время не планируется поддержка Unreal.

---

### Вариант 1 — Мини-SDK с теми же контрактами

Создать новую библиотеку `com.xsolla.android:engine` на основе текущего Android SDK, сохранив те же точки входа (методы, интерфейсы) которые сейчас вызываются из Unity.

**Что делается:**
- Берём только те ~10 методов XLogin и методы XPayments которые реально вызываются из Unity
- Переписываем с Kotlin на Java
- Заменяем зависимости на встроенные Android API:
  - `ktor` / `okhttp` → `HttpURLConnection`
  - `gson` → `org.json.JSONObject`
  - `kotlin-stdlib` → убирается
- Оставляем браузерную часть: CustomTabs, WebView, System Browser, TWA
- Социальные SDK (Facebook, Google, WeChat, QQ) — опционально через `compileOnly`
- Публикуем как AAR на Maven

**Контракты на стороне Unity не меняются** — те же AndroidJavaClass вызовы, те же ProxyActivity классы.

**Размер:** ~2,000-3,000 LOC Java вместо ~10,000+ LOC Kotlin в нескольких модулях.

**Зависимости:** только `androidx.browser` для CustomTabs/TWA.

**Синхронизация с основным SDK:** при добавлении новых фич в основной Android SDK — нужно вручную портировать в мини-SDK. Это основной операционный риск варианта.

---

### Вариант 2 — Мини-SDK с новым контрактом (HTTP → Unity)

Переосмыслить границу между Unity и Android. Android SDK становится тонким UI-клиентом, вся бизнес-логика переносится в Unity C#.

**Что остаётся в Android SDK:**
- Открытие браузера (CustomTabs, WebView, System Browser, TWA)
- Обработка deep link redirect
- Запуск нативных social auth flow (Google, Facebook и др.)
- Возврат auth code / результата в Unity

**Что переносится в Unity C#:**
- HTTP запросы к Xsolla API (через UnityWebRequest)
- Обмен auth code на токен
- Парсинг JSON ответов
- Хранение и refresh токенов

**Зависимости Android SDK:** 0 (только опционально `androidx.browser`).

**Проблема:** при добавлении Unreal — ту же бизнес-логику придётся реализовать на C++. При расхождении реализаций между движками возникают трудноотлаживаемые баги.

**Когда имеет смысл:** если Unity — единственный целевой движок, либо если бизнес-логика достаточно проста чтобы её можно было поддерживать в нескольких местах.

### Вариант 3 — Java классы прямо в Unity

Не создавать отдельную библиотеку. Написать Java классы и положить их в `Assets/Xsolla/Core/Plugins/Android/` по аналогии с уже существующими `PaymentsProxyActivity.java` и `SocialAuthProxyActivity.java`.

**Что делается:**
- Расширяем существующие ProxyActivity классы
- Добавляем нужную логику прямо в Unity репозиторий
- Никакого отдельного AAR, никакого Maven

**Зависимости:** 0 — всё компилируется вместе с Unity проектом.

**Проблема:** при добавлении Unreal придётся написать те же Java классы заново в Unreal репозитории. Нет единой точки изменений — при баге нужно чинить в нескольких местах.

**Когда имеет смысл:** если Unreal и другие движки не планируются, задача одноразовая и скорость важнее архитектуры.

---

### Вариант 4 — Модульный основной SDK

Вместо создания отдельной библиотеки — реструктурировать текущий Android SDK на модули, чтобы Unity и Unreal могли подключать только нужные.

**Пример структуры модулей:**
```
com.xsolla.android:core        — общие утилиты
com.xsolla.android:browser     — CustomTabs, WebView, TWA
com.xsolla.android:payments    — платёжный flow
com.xsolla.android:login       — аутентификация (без HTTP?)
com.xsolla.android:social      — Facebook, Google, WeChat, QQ
```

**Unity подключает:** только `browser`, `payments`, `login`.

**Проблемы:**
- Требует существенного рефакторинга основного Android SDK
- Нужно согласование с Android командой
- Kotlin никуда не уходит
- Транзитивные зависимости уменьшатся, но не обнулятся

**Когда имеет смысл:** если есть ресурс на рефакторинг основного SDK и нужно сохранить единую кодовую базу для мобильных приложений и game engine плагинов.
